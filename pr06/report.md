# Отчет по практической работе №6

## 1. Разбор строки tcpdump

Строка: `12:34:56.789012 IP 127.0.0.1.44321 > 127.0.0.1.8080: Flags [S], seq 123, length 0`

| Поле | Значение | Что означает |
|------|----------|--------------|
| 12:34:56.789012 | 12:34:56.789012 | Время захвата пакета с точностью до микросекунд |
| IP | IP | Протокол сетевого уровня - IPv4 |
| 127.0.0.1.44321 | 127.0.0.1.44321 | IP-адрес источника (127.0.0.1) и порт отправителя (44321) |
| 127.0.0.1.8080 | 127.0.0.1.8080 | IP-адрес назначения (127.0.0.1) и порт получателя (8080) |
| Flags [S] | [S] | Флаг SYN - начало установки TCP-соединения |
| length 0 | 0 | Длина полезной нагрузки (payload) в байтах - 0 байт данных |

## 2. Перехваченные данные HTTP

![Пароль в открытом виде](screens/http-password.png)

Что видно в трафике: В захваченном HTTP-трафике отчетливо видны все передаваемые данные в открытом виде, включая логин admin и пароль supersecret123. Видно тело POST-запроса с параметрами username и password. Кроме того, видны все HTTP-заголовки: User-Agent, Content-Type, Host и другие.

Кто в реальной сети может так же прочитать этот трафик: В реальной сети такой трафик может перехватить злоумышленник в той же локальной сети (при использовании хаба или при ARP-spoofing на коммутаторе), администратор сети с доступом к сетевым устройствам, провайдер услуг интернета, любой кто контролирует маршрутизаторы на пути следования пакетов, злоумышленник взломавший Wi-Fi точку доступа.

## 3. Follow TCP Stream

![Follow TCP Stream](screens/follow-stream.png)

Что видит злоумышленник перехвативший этот трафик: Используя функцию Follow TCP Stream в Wireshark, злоумышленник видит полный диалог между клиентом и сервером. Красным цветом отображаются данные отправленные клиентом, синим - ответы сервера. В красной части отчетливо видны полный HTTP-запрос с методом POST, все переданные параметры: username=admin и password=supersecret123, HTTP-заголовки запроса, весь ответ сервера. Таким образом, злоумышленник получает полную картину взаимодействия, включая учетные данные, и может использовать их для несанкционированного доступа.

## 4. HTTP vs HTTPS --- сравнение

| Что наблюдаем | HTTP (порт 8080) | HTTPS (порт 443) |
|---------------|------------------|------------------|
| IP-адреса сторон | Видны | Видны |
| Порт назначения | Виден (8080) | Виден (443) |
| Заголовки HTTP | Видны полностью | Зашифрованы (не видны) |
| Содержимое запроса (body) | Видно открытым текстом | Зашифровано (не видно) |
| Логин и пароль | Видны полностью | Зашифрованы (не видны) |
| Имя домена (SNI) | Видно в Host: | Видно только в SNI расширении TLS |

## 5. DNS и приватность

Какие домены видны в DNS даже при HTTPS: В DNS-запросах видны все доменные имена, к которым обращается клиент: github.com, example.com, google.com. DNS работает по UDP на порту 53 и передает запросы в открытом виде.

Что это означает для приватности: Даже при использовании HTTPS, злоумышленник может узнать, какие сайты посещает пользователь, просто анализируя DNS-трафик. Это называется утечкой метаданных. Для защиты от этого необходимо использовать DNS-over-HTTPS (DoH) или DNS-over-TLS (DoT), которые шифруют DNS-запросы, либо использовать VPN.

## 6. Base64

Декодированная строка: `dmFzeWE6TXlQYXNzd29yZDIwMjQ=` → `vasya:MyPassword2024`

Почему Base64 не является шифрованием: Base64 - это просто способ кодирования бинарных данных в текстовый формат (ASCII), а не шифрование. Кодирование Base64 не использует секретный ключ, является обратимым без ключа, не обеспечивает конфиденциальность, не скрывает информацию от перехвата. Любой кто перехватил заголовок Authorization с Base64-строкой может декодировать ее за секунду и получить логин и пароль. Вместо Base64 для защиты данных в HTTP необходимо использовать TLS/HTTPS с полноценным шифрованием либо применять более безопасные методы аутентификации такие как токены с ограниченным сроком действия или OAuth.

## 7. tshark vs tcpdump vs Wireshark

| Инструмент | Когда использовать |
|------------|-------------------|
| tcpdump | Когда нет графического интерфейса, для быстрого захвата трафика в консоли, в скриптах автоматизации, на серверах без GUI |
| tshark | На серверах без GUI, когда нужен анализ и фильтрация уже захваченных pcap-файлов в консоли, для автоматизации анализа, работает с display filters |
| Wireshark | При наличии графического интерфейса, для детального визуального анализа, отладки, обучения, исследования сетевых протоколов с удобной навигацией |

## 8. Каналы утечки через сеть

Какие меры защиты закрывают сетевой канал утечки:

1. Использование шифрования TLS/HTTPS для защиты данных
2. Применение VPN для шифрования всего трафика
3. DNS-over-HTTPS (DoH) или DNS-over-TLS (DoT) для защиты DNS-запросов
4. Использование защищенных протоколов аутентификации
5. Настройка брандмауэров для блокировки небезопасных протоколов
6. Сегментация сети для ограничения доступа к чувствительным данным
7. Внедрение системы обнаружения вторжений (IDS)
8. Мониторинг и анализ сетевого трафика на предмет утечек

## 9. Выводы

В ходе выполнения практической работы были достигнуты следующие результаты: освоены базовые навыки работы с сетевыми анализаторами tcpdump, tshark и Wireshark; наглядно продемонстрирована опасность использования незащищенных протоколов (HTTP) - все передаваемые данные (включая логины и пароли) видны в открытом виде; показана важность шифрования трафика - при использовании HTTPS передаваемые данные не видны; выявлены утечки даже при использовании HTTPS - через DNS-запросы видны посещаемые сайты; продемонстрировано, что Base64 не является шифрованием и не обеспечивает защиту данных. Основные выводы: сетевая безопасность требует комплексного подхода. Использование одного протокола HTTPS недостаточно, так как метаданные (DNS, SNI) все равно могут утекать. Для полной защиты необходимо использовать шифрование на всех уровнях: транспортном (TLS), прикладном (HTTPS), и DNS (DoH/DoT). Перехват трафика в локальной сети - реальная угроза, и администраторы должны принимать меры для защиты корпоративных данных.

## 10. Ответы на контрольные вопросы

78. Что такое promiscuous mode и зачем он нужен снифферу? Promiscuous mode (беспорядочный режим) - это режим работы сетевого интерфейса, при котором он принимает все пакеты, проходящие через сетевой сегмент, а не только те, что адресованы его MAC-адресу. Нужен снифферу для захвата всего трафика, проходящего через сеть, независимо от адресата, что позволяет анализировать сетевую активность всех устройств в сегменте.

79. Чем отличается capture filter от display filter в Wireshark? Capture filter применяется во время захвата трафика и определяет, какие пакеты будут сохранены (использует синтаксис Berkeley Packet Filter, как в tcpdump). Display filter применяется уже к захваченным пакетам и только скрывает или показывает их в интерфейсе (использует синтаксис Wireshark), при этом все пакеты остаются в файле захвата.

80. Что такое Follow TCP Stream и для чего используется? Follow TCP Stream - это функция Wireshark, которая собирает все пакеты одного TCP-соединения и реконструирует полный диалог между клиентом и сервером в том порядке, в котором данные были переданы. Используется для анализа содержимого сессии, понимания полной картины обмена данными, восстановления переданных файлов или учетных данных.

81. Почему Base64 в HTTP Basic Auth не является защитой? Что нужно использовать вместо? Base64 не является защитой, потому что это кодирование, а не шифрование - оно обратимо без ключа и не обеспечивает конфиденциальность. Вместо Base64 нужно использовать TLS/HTTPS для шифрования всего канала связи либо применять современные методы аутентификации с токенами (JWT, OAuth) и ограниченным сроком действия.

82. Какие данные утекают даже при использовании HTTPS? Как это исправить? Даже при HTTPS утекают: IP-адреса, порты, доменные имена через DNS-запросы, имя сервера через SNI в TLS-рукопожатии, размер передаваемых данных, время передачи. Для исправления нужно использовать: DNS-over-HTTPS, DNS-over-TLS, ECH (Encrypted Client Hello) для шифрования SNI, VPN для скрытия IP-адресов, padding для маскировки размеров пакетов.

83. Сисадмин говорит: «у нас свитч, а не хаб --- значит сниффинг невозможен». Он прав? Сисадмин не совсем прав. Хотя коммутатор не отправляет весь трафик на все порты (в отличие от хаба), сниффинг все равно возможен через ARP-spoofing/ARP-poisoning, MAC flooding, использование порта SPAN (Port Mirroring), установку физического сниффера между устройствами. Поэтому коммутатор не является полной защитой от перехвата трафика.
